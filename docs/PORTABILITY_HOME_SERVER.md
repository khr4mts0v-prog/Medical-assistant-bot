# Перенос Medical Assistant на домашний сервер

Этот документ фиксирует требования к переносимости проекта. Цель — возможность восстановить приложение на другом Linux-сервере, даже если текущий VPS станет недоступен.

## Что должно храниться в GitHub

В репозитории храним исходный код, React-фронтенд, тесты, зависимости, Docker-конфигурацию, миграции БД, скрипты сборки/развёртывания и документацию. Изменения вносим через ветки и pull request; релизные изменения должны проходить CI.

**Не хранить в GitHub:**
- `.env`, токены, пароли, OAuth-секреты, приватные ключи и сертификаты;
- медицинскую базу, загруженные документы, OCR-тексты, резервные копии и пользовательские логи;
- реальные медицинские данные в тестовых фикстурах.

Секреты должны быть отдельно сохранены в менеджере паролей или в зашифрованном архиве. Не публиковать их в issues, PR, логах и сообщениях.

## Что нужно сохранить отдельно от кода

GitHub — это копия кода, но **не резервная копия данных приложения**. Для полноценного переезда нужны:
1. Актуальная копия репозитория и номер проверенного коммита/релиза.
2. Резервная копия SQLite после корректной остановки записи или через SQLite Online Backup API.
3. Загруженные оригиналы документов и другие пользовательские файлы, если они хранятся вне SQLite.
4. Зашифрованная копия настроек окружения без публикации секретов.
5. Сведения о домене/DNS, TLS, OAuth redirect URI, Telegram webhook/polling и внешних API, если они используются.
6. Проверенная инструкция восстановления и результаты тестового восстановления.

Резервные копии медицинских данных хранить в зашифрованном виде, отдельно от сервера приложения, с ограниченным доступом. Периодически проверять восстановление на тестовом экземпляре. Не переносить реальные данные в тестовую среду без необходимости.

## Целевая схема домашнего развёртывания

- Linux на домашнем сервере.
- Docker Engine и Docker Compose.
- Отдельные сервисы для веб-приложения и Telegram-бота.
- Постоянные тома для SQLite и пользовательских файлов.
- Конфигурация через локальный `.env` с ограниченными правами доступа.
- Health checks, логи без медицинского содержимого и документированный backup/restore.
- React как единый фронтенд; FastAPI/Python остаётся серверной частью.

Домашний сервер не обязательно должен быть доступен из интернета. Для личного доступа можно предусмотреть VPN; публичный доступ потребует отдельной настройки TLS, firewall, обновлений и защиты авторизации.

## План переноса

1. Завершить миграцию интерфейса на React без изменения медицинской бизнес-логики.
2. Проверить, что все исходники, зависимости, Docker-конфигурация, тесты и скрипты находятся в GitHub и собираются из чистого клона.
3. Зафиксировать версии Python, Node.js, системных OCR-пакетов и Docker-образов.
4. Подготовить шаблон `.env.example` только с названиями переменных и безопасными заглушками.
5. Подготовить автоматизированные backup/restore для SQLite и файлов документов.
6. Поднять тестовую копию на домашнем сервере из чистого клона, восстановить тестовый архив и прогнать smoke-тесты.
7. Только после проверки планировать перенос реальных данных. Исходный VPS и его данные не удалять, пока восстановление не подтверждено.

## Критерий готовности

Переезд считается подготовленным, когда можно с чистого Linux-хоста клонировать репозиторий, собрать и запустить приложение, восстановить резервную копию в тестовой среде и пройти тесты без доступа к исходному VPS.
