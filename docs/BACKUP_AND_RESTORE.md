# Резервное копирование и восстановление Medical Assistant

Цель: восстановить код на новом сервере из GitHub, а приложение и документы — из отдельной защищённой резервной копии. **GitHub не является резервной копией пользовательских данных.**

## 1. Какую версию клонировать

Репозиторий: https://github.com/khr4mts0v-prog/Medical-assistant-bot

- Стабильная база для развёртывания: `release/web-2026-10`.
- Для продолжения текущей разработки используйте явно выбранную рабочую ветку или её зафиксированный commit SHA.
- Не клонируйте без указания ветки и не считайте `main` актуальной версией веб-приложения: default branch может отставать от релизной ветки.
- Незавершённые PR и их ветки не равны одобренному релизу. Не переключайте production на ветку тестов только ради восстановления кода.

Пример клонирования стабильной базы:

```bash
git clone --branch release/web-2026-10 --single-branch \
  https://github.com/khr4mts0v-prog/Medical-assistant-bot.git
cd Medical-assistant-bot
```

Проверка исходников без запуска приложения:

```bash
git rev-parse HEAD
python scripts/check_portability.py
python -m compileall -q .
python -m unittest discover -s tests -v
```

Путь к тесту классификатора и дополнительные проверки смотрите в `README.md` и `docs/PORTABILITY_HOME_SERVER.md`.

## 2. Что хранить отдельно от GitHub

Не коммитьте и не загружайте в публичные issues/PR:

- `.env`, токены, пароли, OAuth client secrets, TLS private keys;
- `data/archive.sqlite3`, другие базы и содержимое каталога `data/`;
- оригиналы медицинских документов, OCR-текст, журналы и резервные копии;
- реальные медицинские данные в тестовых фикстурах.

Отдельно и безопасно сохраните:

1. Зашифрованную резервную копию каталога `data/` (включая SQLite, оригиналы, OCR sidecars и прочие runtime-файлы).
2. Копию настроек `.env` в менеджере паролей или в отдельном зашифрованном хранилище.
3. Точное значение `FERNET_KEY`, которым зашифрована существующая база. Без исходного ключа зашифрованные поля восстановить нельзя.
4. Настройки домена/DNS, TLS, OAuth redirect URI и используемых внешних сервисов — без размещения секретов в GitHub.

Храните резервную копию вне исходного VPS, в зашифрованном виде и с ограниченным доступом. Копия, оставшаяся только на арендуемом сервере, не защищает от его отключения.

## 3. Создание резервной копии данных

Перед копированием запланируйте короткое окно обслуживания. Пример для текущей Docker Compose-конфигурации; выполнять вручную на сервере, где фактически расположены данные:

```bash
cd /opt/medical-assistant-bot
umask 077
BACKUP_DIR="$HOME/medical-archive-backup"
mkdir -p "$BACKUP_DIR"
```

Остановите сервисы, чтобы приложение не меняло SQLite и файлы во время снимка:

```bash
docker compose stop medical-archive medical-archive-web
```

Создайте зашифрованный архив всего каталога данных. Команда попросит ввести пароль шифрования; используйте сильный уникальный пароль и сохраните его отдельно:

```bash
tar -C /opt/medical-assistant-bot -czf - data \
  | gpg --symmetric --cipher-algo AES256 \
      --output "$BACKUP_DIR/medical-archive-data.tar.gz.gpg"
```

Проверьте, что зашифрованный файл существует и имеет ненулевой размер, затем скопируйте его на другое устройство или в отдельное защищённое хранилище. Не удаляйте исходные данные до проверки копии. После создания архива запустите сервисы снова:

```bash
cd /opt/medical-assistant-bot
docker compose start medical-archive medical-archive-web
docker compose ps
```

Если команда архивирования завершилась ошибкой, не считайте резервную копию готовой. Убедитесь, что сервисы снова запущены, и повторите процедуру. При необходимости резервного копирования других каталогов сначала проверьте фактические bind mounts и пути в Compose.

## 4. Восстановление на новом сервере

1. Установите поддерживаемые ОС, Docker Engine и Docker Compose.
2. Клонируйте нужную ветку из раздела 1.
3. Создайте локальный `.env` на основе `.env.example` и установите права доступа:

   ```bash
   cp .env.example .env
   chmod 600 .env
   ```

4. Внесите реальные секреты из защищённого хранилища. Для восстановления существующей базы используйте **исходный `FERNET_KEY`**, а не новый. Не копируйте `.env` в репозиторий.
5. Скопируйте зашифрованный архив на новый сервер. Расшифруйте его в защищённом временном месте, используя пароль резервной копии, затем проверьте содержимое архива до распаковки.
6. Остановите Compose-сервисы и восстановите каталог `data/` в корень клона. Не распаковывайте поверх существующих данных без отдельной резервной копии назначения.
7. Проверьте конфигурацию и запустите сервисы:

   ```bash
   docker compose config --quiet
   docker compose up -d --build
   docker compose ps -a
   docker compose logs --tail=100 medical-archive-web
   ```

8. Проведите проверку восстановления: доступ к базе, наличие ожидаемых записей, открытие нескольких выбранных оригиналов, работоспособность OCR-поиска и авторизации. Не отправляйте реальные документы внешнему ИИ во время smoke-теста.
9. Если восстановление не прошло, остановите новый экземпляр и разберите ошибку, не удаляя исходную резервную копию. Старый сервер и его данные не удаляйте до успешной проверки.

После распаковки зашифрованного архива удалите временные незашифрованные копии безопасным способом, соответствующим файловой системе и носителю. Не оставляйте их в публичных каталогах или временных каталогах общего доступа.

## 5. Критерий готовности

Восстановление считается проверенным только после успешного клонирования нужного commit, сборки приложения из чистого checkout, восстановления `data/` и проверки авторизации, базы и оригиналов. Успешный CI подтверждает тесты и сборку кода, но не доказывает восстановимость реальных данных.
